---
title: Credentials that left through the wrong door, and a locked URL that was not locked
version: 2.8.1
---

A security patch for 2.8.0. Three defects exposed credentials or the network behind a Bowire: internal plugin configuration — private keys and secret keys among it — went to the target as request headers, history and recordings kept resolved credentials in clear text, and a workbench with a locked server URL still dialed any URL a caller named. Upgrading is recommended for every 2.8.0 installation, and urgently for one that uses mTLS or AWS SigV4 auth, or that runs with `LockServerUrl`. Everything 2.9 brings stays on `main`; this release carries only the fixes ([#759](https://github.com/Kuestenlogik/Bowire/issues/759)).

## Security

### Plugin configuration no longer reaches the target as headers

The workbench hands a protocol plugin its configuration in the same bag as the call's headers: `__bowireMtls__` carries the client certificate *and its private key*, `__bowireAwsSigV4__` the AWS secret key, `__bowireCookieEnv__` the cookie-jar id. REST and gRPC took their own entries out before sending. GraphQL, SSE, JSON-RPC, SignalR, WebSocket, Connect / gRPC-Web and MCP copied the whole bag onto the request — so with mTLS or SigV4 auth configured in the environment and one of those protocols, the key material went to the target server as literal headers.

Every path that turns metadata into wire headers now goes through one filter that drops every `__bowire*` entry, including entries the plugin in question does not itself understand. A regression test calls a real SSE server and checks the header names it received.

**If you used mTLS or AWS SigV4 auth with GraphQL, SSE, JSON-RPC, SignalR, WebSocket, gRPC-Web / Connect or MCP on 2.8.0 or earlier, treat that private key or secret key as disclosed to the servers you called, and rotate it.**

### History and recordings keep no credentials

History lives in the browser's `localStorage`, and recordings are stored and exported; both kept the call's metadata after the auth helper had resolved it. That meant resolved `{{secret.*}}` and keyring values wherever they appeared, and the internal entries above. History now stores credential headers (`Authorization`, `Cookie`, API-key headers and the like) only as a placeholder, replaces resolved secret and keyring values with `***` in headers, body and messages, and never stores an internal entry; recordings drop the internal entries too. Replaying a history entry applies the environment's current auth again, so the credential is resolved fresh rather than read back from storage.

History written by 2.8.0 is not rewritten; clear it (Settings → Data) if it may hold credentials.

### A locked server URL is enforced by the server

`LockServerUrl` made the URL field read-only in the workbench, but the endpoints still dialed whatever `?serverUrl=` a caller passed — a locked Bowire was an open relay into its host's network, the cloud metadata endpoint included. Every endpoint that dials a target now checks it first: invoke, stream, channel open, discovery, fuzzing and parallel runs. A target outside the allowed set is refused with `403` (`urn:bowire:target-not-allowed`).

The allowed set is `ServerUrl` and `ServerUrls`, plus the new `AllowedServerUrls` (`Bowire:AllowedServerUrls`, or `--allowed-server-url`, repeatable), plus the host's own origin in embedded mode. Setting `AllowedServerUrls` alone enforces it without locking the field. An unlocked Bowire without the option behaves as before.
