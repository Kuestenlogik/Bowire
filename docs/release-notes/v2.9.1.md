---
title: Packages that no longer bring a known advisory with them
version: 2.9.1
---

A security patch for 2.9.0. Several published packages pulled dependencies with known advisories into every project that referenced them — the OpenAPI adapters a YAML reader open to a denial of service, the OIDC provider and the SignalR adapter vulnerable `System.Security.Cryptography` and SignalR packages. 2.9.1 raises each of them to a fixed version, makes sure the fixed version is what a consumer of the package actually resolves, and lets the build fail on any advisory from now on. Upgrading is recommended for every 2.9.0 installation, and especially for a project that references the OpenAPI adapters or `Kuestenlogik.Bowire.Auth.Oidc`. There is no new feature and no breaking change; besides the dependencies, 2.9.1 carries the fixes, translations and documentation that landed on `main` since 2.9.0.

## Security

### The OpenAPI adapters read YAML with a fixed reader ([#798](https://github.com/Kuestenlogik/Bowire/issues/798))

`Microsoft.OpenApi.YamlReader` before 3.10.0 (and before 2.12.0 on the 2.x line) expands YAML aliases without a limit, so a crafted OpenAPI document can exhaust memory while it is parsed — [GHSA-7pxr-59rr-hqj2](https://github.com/advisories/GHSA-7pxr-59rr-hqj2), high. Bowire reads the OpenAPI documents of the services you point it at, so a hostile or broken document was enough. `Kuestenlogik.Bowire.Protocol.Rest.OpenApi3` now depends on `Microsoft.OpenApi` and `Microsoft.OpenApi.YamlReader` 3.10.2 (was 3.8.0), `Kuestenlogik.Bowire.Protocol.Rest.OpenApi2` on 2.12.2 (was 2.9.0). Examples in an OpenAPI 3.0 document are read exactly as before.

### Cryptography and SignalR packages raised to their fixed versions ([#780](https://github.com/Kuestenlogik/Bowire/issues/780), [#808](https://github.com/Kuestenlogik/Bowire/issues/808))

The 2.9.0 packages resolved `System.Security.Cryptography.Pkcs` 10.0.10 ([GHSA-846f-f764-76mx](https://github.com/advisories/GHSA-846f-f764-76mx), high; [GHSA-2fmv-rv2c-59x7](https://github.com/advisories/GHSA-2fmv-rv2c-59x7), moderate), `System.Security.Cryptography.Xml` 10.0.10 ([GHSA-r955-8q5j-3h83](https://github.com/advisories/GHSA-r955-8q5j-3h83), high) and `Microsoft.AspNetCore.SignalR.Common` 10.0.12 ([GHSA-334f-vvp4-7g6p](https://github.com/advisories/GHSA-334f-vvp4-7g6p)). Every `Microsoft.AspNetCore.*` dependency moves to 10.0.13, the runtime patch of the .NET SDK 10.0.402 the packages are built with.

`Kuestenlogik.Bowire.Auth.Oidc` now depends on `System.Security.Cryptography.Pkcs` and `System.Security.Cryptography.Xml` 10.0.13 directly, because `Microsoft.Identity.Web` still asks for 10.0.10. The Xml dependency needed a second look: the .NET 10 SDK drops a dependency from a package when the project itself gets it from the ASP.NET Core shared framework, so the first fix held inside the repository and never reached the nuspec — a project that referenced the package without referencing the shared framework itself still resolved Xml 10.0.10. The package now lists it, and a project referencing `Kuestenlogik.Bowire.Auth.Oidc` alone reports no vulnerable package.

### The build fails on a known advisory ([#781](https://github.com/Kuestenlogik/Bowire/issues/781))

The advisories above went unnoticed because the build suppressed NuGet's audit warnings for every project. That suppression is gone: NuGet audit checks the whole dependency graph, direct and transitive, at every severity, and a package with a known advisory fails the restore. The analyzer warnings the blanket suppressions had hidden were fixed at their cause, so the Release build is clean without them. `dotnet list package --vulnerable --include-transitive` reports nothing for 2.9.1, and every package was checked on its own as a consumer sees it.

## Also in this release

### Locked targets cover the auth helpers too

2.8.1 made `LockServerUrl` and `AllowedServerUrls` bind every endpoint that dials a target. The helpers that call an identity provider on the caller's behalf — the OAuth token, code-exchange and refresh proxies, the custom-token proxy, auth-flow capture and the connection check under **Settings → Network** — were still free to call any URL. They now obey the same restriction. Token endpoints rarely live on the API's host, so they get a list of their own: `AllowedAuthUrls` (`Bowire:AllowedAuthUrls`, or `--allowed-auth-url`, repeatable). While a restriction is active the helpers follow no redirect, so a `302` cannot lead past the check. A refused call is a `403` (`urn:bowire:target-not-allowed`) that now names the setting and the command-line flag that would allow the target, and the tool's start banner says when targets are locked and no auth URL is listed yet.

### One language, one pitch, one licence ([#777](https://github.com/Kuestenlogik/Bowire/issues/777), [#778](https://github.com/Kuestenlogik/Bowire/issues/778), [#668](https://github.com/Kuestenlogik/Bowire/issues/668), [#647](https://github.com/Kuestenlogik/Bowire/issues/647))

The German left in comments, configuration notes and a few documentation passages is English now; the shipped German UI catalogue stays, as do the German words the scaffold parser recognises. The package descriptions carry the same one-line pitch as the README and the site — *the API workbench that embeds in your own service* — while the product keeps describing itself inside a host as a multi-protocol API workbench. Bowire stays Apache-2.0 throughout, and every source file says so in its header.

### Building from source ([#797](https://github.com/Kuestenlogik/Bowire/issues/797))

`global.json` pins the .NET SDK 10.0.402 with `rollForward: latestFeature`: a newer patch or feature band builds as well, an older SDK is refused with a clear message.
